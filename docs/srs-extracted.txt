Software Requirements Specification: Student Activity Platform
Nov 23, 2026 · @Nathaniel Klobodu
1. Introduction
The platform lets an instructor release up to two activities per week to a class. A student opens them by entering an index number, and only while the time window is open and only from inside the location the instructor chose.
1.1 Purpose
This SRS defines what the system must do, the data it keeps, and the limits it works under. It is the single reference for design, build and acceptance testing over the remaining four lessons.
1.2 Scope
In scope
Weekly activity scheduling per class, with a maximum of 2 activities per week.
Student self-registration and access by index number and class code.
Access control by time window and by geofence (centre point and radius set by the admin).
Activity delivery, automatic scoring on the server, and instant score feedback to the student.
An admin console for classes, rosters, weeks, activities, geofences, live results and Excel export.
Out of scope for this release
Student passwords, roster uploads by the admin and email notifications.
Native mobile apps.
Proctoring, camera or microphone access.
Learning management system integration (for example grade sync to a university portal).

2. Overall description
2.1 Product perspective
The platform is a new standalone web application built with Next.js and Supabase. It replaces the earlier single-laptop prototype. The three activities from that prototype (CIA sorting, risk rating, password strength) become the first activity types, so existing content carries over.

2.3 Operating environment
Students use a phone or laptop with a current Chrome, Safari, Firefox or Edge. Android Chrome and iOS Safari are the priority.
The site is served over HTTPS. Browsers only share location on secure pages.
Students grant the browser location permission when asked.
The admin console targets a laptop screen and stays usable on a phone.
All times are stored in UTC and shown in Africa/Accra time, which has no daylight saving.
2.4 Constraints
Framework: Next.js (App Router, TypeScript). Database and admin authentication: Supabase.
A week holds at most 2 activities. The database enforces this, and the interface does not offer a third.
Roughly four lessons remain, so the first release must be usable in the next lesson and grow week by week.
Hosting uses free or low-cost tiers. Student pages stay light because many students are on mobile data.
The minimalist black and white visual language in section 5 applies to every screen.
2.5 Assumptions and dependencies
Index numbers are unique within the university. Students type their own index number and name, so the system holds no prepared list of index numbers.
A class has up to about 150 students using the system at the same time. The admin confirmed this number, and it sizes the database plan.
Campus connectivity is good enough for a page load and a small form submission.
Students are physically in the classroom when the window is open. A student who cannot share location needs an admin override (FR-24).
The system provides deterrence against remote access. It cannot prove a position, because location data comes from the student's own device (see section 6.1).

4. Data requirements
Supabase Postgres holds eight tables. A week owns at most two activities, and a student is identified only by the index number the student registers with.
Table
Key columns
Notes
classes
id, name, join_code, default_lat, default_lng, default_radius_m
One row per course offering. The default location seeds each new week.
students
class_id, index_number, name, name_key, registered_at
Primary key (class_id, index_number). A row is created when the student registers. Index numbers are stored trimmed and uppercase. name_key is the name in lowercase without extra spaces, used to detect a different person claiming the same number.
weeks
id, class_id, number, title, opens_at, closes_at, published, link_token, geofence_enabled, center_lat, center_lng, radius_m, max_accuracy_m
Unique (class_id, number). Times are timestamptz. link_token is a unique random string used in the week link. max_accuracy_m defaults to 100.
activities
id, week_id, position, type, title, instructions, config, answer_key, max_attempts, max_score
position is 1 or 2 with a check constraint. Unique (week_id, position) enforces the cap. config and answer_key are jsonb.
attempts
id, activity_id, class_id, index_number, attempt_no, started_at, submitted_at, auto_submitted, answers, score, max_score, feedback, flagged, flag_reason
Unique (activity_id, index_number, attempt_no). One row per submission.
access_events
id, class_id, week_id, index_number, event, allowed, reason, lat, lng, accuracy_m, distance_m, ip_hash, user_agent, created_at
event is login, start or submit. Written for allowed and denied checks.
overrides
id, week_id, class_id, index_number, kind, reason, expires_at, created_by
kind is geofence or time. Read on every access check.
admins
user_id, email
Links Supabase Auth users to console access.
Data rules
Row Level Security is on for every table with no policy for the public (anon) role. Browsers never query the database directly.
Student requests go through Next.js server code that uses the Supabase service role key. That key exists only in server environment variables.
answer_key is read only by scoring code on the server.
The cap of two activities per week is a database constraint, so no code path can exceed it.
IP addresses are stored as salted hashes. Coordinates are rounded to 4 decimal places.
Location rows in access_events are deleted 90 days after the course ends. Confirm this period with the university.
The admin exports scores before the end of the semester. Database backups follow the Supabase plan in use.

The student flow is mobile first, single column, with touch targets of at least 44 px.
Text contrast meets WCAG 2.1 AA. Light grey body text must still reach 4.5:1 on white.
Every control works by keyboard with a visible focus ring. Drag and drop has a tap or keyboard alternative.
Error messages say what happened and what to do next.

6. Non-functional requirements
6.1 Security and the limits of geofencing
The position a student reports comes from their own device. A student with a location-spoofing app or a modified browser can fake it, so the geofence deters casual remote access and does not prove presence. The system reduces the risk with these measures:
The server, never the browser, decides whether a position is inside the radius.
Readings with poor accuracy are rejected (FR-16).
The position is checked at login, at activity start and at submission, and every result is logged for review (FR-17, FR-20).
Submissions from outside the area are flagged in the admin console.
The class code, written on the board at the start of the lesson, is required at registration, so a remote student cannot register without it. The admin can change the code at any time.
Indoor accuracy varies. Phones usually report 5 to 30 m. Laptops often rely on Wi-Fi positioning and can be off by hundreds of metres. Set the radius to cover the whole building, 100 m or more, and test it from the back row of the classroom before the first lesson.
General security rules:
HTTPS everywhere. Session cookies are httpOnly, Secure and SameSite=Lax. A week link carries a random token of 12 characters that cannot be guessed. The link opens the sign-in page only. Time window, geofence and class code still apply to everyone who opens it.
Every input is validated on the server with a schema. Admin changes also check the request origin.
Secrets live in server environment variables only. The service role key never reaches the browser.
Answer keys never appear in any response sent to a student.
Admin accounts require multi-factor authentication.
Login rate limits count per index number (10 attempts per 10 minutes). The per-IP limit is set high, because a whole class shares one campus network address.
6.2 Privacy
Collected data: index number, name the student enters, rounded coordinates at each check, a hashed IP address and the browser user agent. The purpose is access control and attendance evidence.
A plain notice appears before the browser asks for location. It states what is collected, why, and for how long.
Only the admin can read location data.
Retention: location records are removed 90 days after the course ends. Scores follow the department's record rules.
Check the design against the Data Protection Act, 2012 (Act 843) and university policy before the first lesson.

6.4 Reliability
The system should have no planned downtime during a window.
The student's answers are kept in the browser while they work. A failed submission retries automatically and the student sees its state.
Submitting is idempotent. A double tap or retry cannot create a duplicate attempt.
The countdown uses the server clock offset measured at page load.
A scheduled Supabase backup and an Excel export after each lesson protect the scores.
6.5 Maintainability and compatibility
Each activity type is a module with a configuration schema, a student renderer and a server scorer. A new weekly activity of an existing type needs configuration only.
Automated tests cover the haversine distance, window checks, attempt limits and every scorer.
Supported browsers: the two latest versions of Chrome, Edge, Firefox and Safari, and Chrome on Android and Safari on iOS.
7. System architecture
Next.js on Vercel serves the interface and a thin server layer. Supabase stores the data. Every student request passes through server code that checks session, window and location before it touches the database.

Every request to start or submit an activity runs the same ordered checks. The first failure stops the request and returns its reason.
The session cookie is valid and belongs to a registered student of this class.
The week is published and the window is open, or a time exception applies.
The reported position is accurate enough and inside the radius, or a geofence exception applies, or the geofence is off.
The student has attempts left on this activity.
For a start, the server sends the activity without its answer key. For a submit, the server scores it, saves the attempt and returns the result.
